# go.services.communication.dzen

communication_services это сквозная демонстрация путешествия сообщения через распределённую систему.

## О проекте
**Цель проекта** — показать, как одно событие, клик читателя по автору, проходит путь от генерации до отображения на экране. На каждом шаге событие трансформируется, обогащается и превращается в полезные данные.

Система состоит из нескольких сервисов-звеньев. Каждое звено имеет свою роль, зону ответственности и свой язык общения с соседями.

## Архитектура
Кратко:

`ClickGenerator / ClickScenario -> Kafka -> ClickCounter -> 
ClickStorage -> PostgreSQL -> ClickDashboard -> UI`

## Звено 1. Генераторы кликов
Первое звено представлено двумя взаимозаменяемыми сервисами: ClickGenerator и ClickScenario. Они имеют практически идентичную структуру, создают клики и отправляют их в Kafka.

### ClickGenerator
Имитирует активность читателей случайным образом на основе заранее установленных конфигураций. Конфигурации хранятся в config.json. В конфигурациях определяются количество наборов ID читателей и читаемых авторов, количество чтений, ожидание и ретраи.

Назначение сервиса — создание моделируемой нагрузки, например на 10 000 или 100 000 пользователей. Также он позволяет проверить устойчивость Kafka и всей системы при одновременных запросах.

#### Бизнес-логика:

- В usecase.go Simulator.Run запускает по горутине на каждого reader_id.

- Внутри runReaderGoroutine случайно выбирается число чтений.

- В цикле выбирается случайный author_id.

- На каждое чтение создаётся отдельная горутина.

- Отправка выполняется через sendWithRetry.

- Между чтениями выдерживается задержка из конфига.

- readWg.Wait() ждёт завершения всех отправок.

- sendWithRetry выполняет до 5 попыток с context.WithTimeout и экспоненциальным backoff.

- Атомарный счётчик completedReaders показывает прогресс.

#### Связь:

Случайные клики направляются через продюсер в Kafka в kafka.go. Перед запуском создаётся топик, если он ещё не создан, в topic.go. В топике создаётся 8 партиций, есть проверка, что партиций именно 8.

### ClickScenario
Запускает заранее известный сценарий, что позволяет всегда получать одинаковый детерминированный результат.

Назначение сервиса — детерминизм и сквозная проверяемость. Можно запускать один и тот же сценарий, пропускать его через все сервисы и убеждаться, что итоговая таблица на странице всегда одинаковая. Это демонстрация того, что распределённая система может быть воспроизводимой, идемпотентной и проверяемой от начала до конца.

#### Бизнес-логика:

В usecase.go Simulator принимает сценарии.

Run запускает по горутине на каждого пользователя.

Внутри перебираются авторы строго в порядке из сценария.

Каждое чтение выполняется в отдельной горутине.

В loader.go LoadScenarios читает все *.scenario, сортирует лексикографически и парсит каждый файл.

#### Связь:

Клики по сценарию направляются через продюсер в Kafka в kafka.go. Перед запуском создаётся топик, если он ещё не создан, в topic.go. В топике создаётся 8 партиций, есть проверка, что партиций именно 8.

## Звено 2. Kafka
В docker-compose.yml поднимаются три брокера: kafka1, kafka2, kafka3. Режим работы — KRaft.

## Звено 3. ClickCounter
Сервис-агрегатор, который собирает данные из Kafka и считает их.

#### Бизнес-логика:

- Счётчик представлен трекером в tracker.go.

- Трекер имеет мьютекс для потокобезопасной работы.

- Внутри хранится карта с датами и авторами, а также множество уникальных пользователей.

#### Связь:

Принимает данные через Consumer, который читает из Kafka.

- StartOffset: kafka.FirstOffset позволяет при падении и перезапуске сервиса всегда читать сообщения с начала.

Отдаёт данные через ручку StatsHandler.

- GET /stats по запросу отдаёт статистику за вчерашний день.

- Принимает query-параметр author_ids, например ?author_ids=1,2,3.

- Параметр парсится: разбивается по запятой, обрезаются пробелы, значения преобразуются в int64. Если что-то не так — возвращается 400.

- Затем вызывается tracker.GetYesterdayStats, формируется ответ в виде JSON-массива AuthorStat с полями author_id и count, и отдаётся клиенту.

## Звено 4. ClickStorage
Забирает статистику из ClickCounter по HTTP и сохраняет в PostgreSQL. Обновление выполняется при старте и ежедневно в 00:10 / 01:10 UTC. Повторный прогон идемпотентен.

#### Бизнес-логика:

В service.go UpdateStatsForDate получает авторов, режет их на батчи по StatsBatchSize.

Для каждого батча делает HTTP-запрос к ClickCounter и сохраняет данные через UpsertStatsBatch.

В repository.go UpsertStatsBatch выполняет условный UPSERT:
ON CONFLICT ... DO UPDATE SET clicks = EXCLUDED.clicks WHERE stats.clicks < EXCLUDED.clicks.

Обновляет только если новое значение больше.

Вставка выполняется батчем в транзакции.

#### Связь:

В service.go осуществляется запрос к ClickCounter.


## Звено 5. PostgreSQL

Хранилище агрегированной статистики. Сюда `ClickStorage` записывает данные, отсюда `ClickDashboard` читает их для отдачи фронтенду.

Схема создаётся и обновляется через миграции. Миграции применяются только сервисом `ClickStorage`, чтобы избежать гонок и конфликтов между сервисами.

Бизнес-логика:

- `ClickStorage` выполняет запись через UPSERT.
- `ClickDashboard` выполняет только чтение.
- Таблица статистики является контрактом между сервисами.

Связь:

- `ClickStorage` → PostgreSQL: запись и обновление агрегатов.
- `ClickDashboard` → PostgreSQL: чтение агрегатов для API.


## Звено 6. ClickDashboard
Витрина: читает агрегаты из PostgreSQL и отдаёт их фронтенду.

#### Связь:

- handlers.go — обёртка над StatsService.

- GetStats(w, r) — обработчик GET /stats.

- Имеет CORS, так как страница открывается отдельно от сервиса.

- Читает query-параметр days. По умолчанию 5. Если параметр передан и это положительное число — используется он.

- Логирует запрос.

- Затем вызывает service.GetStats(days). Если ошибка — 500. Иначе отдаёт JSON.

#### Бизнес-логика:

- В models.go описаны три структуры:

- Author с полями ID, Email, FirstName, LastName;

- StatsResponse с полями Dates — массив строк и Authors — массив AuthorStats;

- AuthorStats с полями ID, Name и Clicks — массив чисел.

- Это формат, удобный для рендеринга: по оси X — даты, по оси Y — клики, каждая линия — автор.

## Звено 7. UI дашборда
Статическая HTML-страница, которая запрашивает данные у ClickDashboard и рисует таблицу. Это не сервис, а файл index.html, который существует независимо от остальных сервисов. Он может существовать сам по себе, но без сервиса не будет заполняться данными.

Страница обращается к ClickDashboard по адресу http://localhost:8085 и вызывает ручку /stats с параметром days. Если дашборд жив и отвечает — данные приходят, и таблица строится. Если дашборд не запущен, упал или недоступен — страница покажет ошибку в блоке errorMsg, а таблица не построится. Страница не ломается и не падает, она просто не может показать данные, потому что их неоткуда взять.

## Заключение
Проект показывает путешествие одного сообщения. Читатель в ClickScenario или ClickGenerator нажимает на клик, генератор превращает это в ClickRequest, Kafka принимает его с ключом по автору, ClickCounter читает и дедуплицирует по уникальным пользователям, ClickStorage раз в сутки забирает агрегат и кладёт в PostgreSQL, ClickDashboard достаёт его и отдаёт по HTTP, а статическая страница рисует таблицу.

Используются несколько способов передачи данных: Kafka, HTTP, PostgreSQL и прямая передача на страницу.

Проект — это учебный стенд, стресс-полигон и референсная архитектура одновременно. На нём можно изучать Kafka, HTTP, PostgreSQL, миграции, планировщики, идемпотентность, детерминизм, graceful shutdown, CORS и многое другое.

Ценность проекта в том, что он превращает абстрактные слова «распределённая система» в конкретный маршрут, который можно пройти от начала до конца, потрогать руками, сломать, починить и снова запустить.
